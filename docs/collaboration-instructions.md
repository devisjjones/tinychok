# Collaboration Instructions

Короткая памятка по тому, как давать владельцу проекта ручные инструкции и как формулировать проверки.

Для продолжения работы в новом чате есть отдельная операционная памятка: [docs/new-thread-runbook.md](/Users/devisjjones/Documents/tinychok/docs/new-thread-runbook.md).

## Автотесты Как Gate

- если задача не `docs-only`, нельзя писать `готово`, `исправлено` или `задеплоено`, пока локально не зелёный `npm run test:gate`
- во время коротких итераций можно отдельно гонять `npm run test:ui-contracts`, но он не заменяет полный gate
- если меняется продуктовый или UI-контракт, перед `npm run test:gate` сначала нужно добавить или обновить автотест
- staging deploy не начинать, пока `npm run test:gate` не прошёл
- в финальном ответе всегда перечислять, какие именно автотесты были запущены

## Последовательность Задач

- держать одну активную пользовательскую задачу за раз
- если пользователь прислал следующую задачу до отчёта по текущей, сначала явно закрыть статус текущей задачи
- не склеивать несколько выполненных задач в один общий итог без явного разделения

## Формат Отчёта Про Автотесты

- в каждом финальном ответе отдельной строкой писать блок `Автотесты`
- в блоке `Автотесты` указывать актуальные числа последнего прогона:
  - `npm run test:ui-contracts = <N>`
  - `npm run test:gate = <M>`
- отдельной строкой писать блок `Покрытие`
- в блоке `Покрытие` явно указывать:
  - `добавил новый тест`
  - или `усилил существующий тест`
- отдельно коротко писать, что именно покрыто этим тестом или усилением
- если число `tests` не выросло, потому что были добавлены `assert` внутри уже существующего `test(...)`, это тоже нужно проговаривать явно

## Формат Ручных Инструкций

- если действие должен выполнять человек, инструкции разбиваются на отдельные блоки `Шаг 1`, `Шаг 2`, `Шаг 3`
- один шаг должен описывать один логический кусок действий
- если нужна визуальная проверка, после нужного шага нужно просить скриншот
- если проверка зависит от UI-состояния, полезно просить скрин сразу после ключевого действия, а не только в самом конце

## Когда Просить Жёсткое Обновление

- после правок иконок
- после правок аватаров
- после обновлений emoji picker, GIF picker и другой свежей статики
- после изменений viewer-а, шрифтов и локальных asset-файлов

## Как Проверять Server-Driven UI

Если механика завязана на snapshot, realtime или lazy history, полезно просить отдельные скрины:

- сразу после входа в комнату
- после скролла вверх и догрузки истории
- после reload страницы

Это помогает отделять локальный optimistic state от реально сохранённого server state.

Для admin UI тот же принцип особенно важен на:

- `Сводке`, если проверяются агрегаты по каналам / группам / тредам
- `Жалобах`, если проверяется unread badge и снятие unread после открытия тикета
- `Медиа`, если проверяется `Hide` / `Delete`

## Как Проверять Scroll / Overflow

Если правка касается ленты комнаты, списков, fixed-shell layout или mobile touch scrolling, проверка должна быть двухконтурной:

1. desktop:
   - wheel / trackpad scroll внутри комнаты
   - scroll вверх к старым сообщениям
   - возврат вниз после собственного сообщения
2. mobile:
   - scroll пальцем внутри комнаты
   - scroll в списках / настройках / каналах, если менялся общий shell
   - отсутствие document-overscroll поверх pinned viewport

Что нельзя делать:

- нельзя считать scroll-поправку проверенной только по скрину
- нельзя считать scroll-поправку проверенной только по `npm run test:ui-contracts`
- нельзя вносить широкий `touch-action` фикс без отдельной проверки desktop и mobile

## Как Проверять Delete Flow

Delete-path нельзя считать проверенным только по исчезновению элемента из UI.

Нормальный сценарий проверки:

1. удалить сообщение или пост;
2. выйти из комнаты;
3. зайти в комнату снова;
4. при необходимости сделать hard reload;
5. только после этого считать delete-path починенным.

Если delete / hide проверяется из admin moderation queue, нужно отдельно просить:

- скрин тикета до действия
- скрин общего чата или канала после действия
- reload комнаты
- повторный скрин после reload

## Как Проверять Media Flow

Для фото, файлов, GIF и viewer-а полезно просить отдельные скрины:

- preview до отправки
- сообщение после отправки в ленте
- fullscreen viewer после tap
- ошибка при oversized / unsupported file, если проверяется validation path

Если тестируется admin moderation для media, полезно дополнительно просить:

- скрин карточки media в admin
- скрин audit log после `Скачать` или `Посмотреть`
- скрин самого чата после `Hide` или `Delete`

## Как Проверять Admin Flow

Для admin панели лучше просить скрины кусками, а не одной длинной прокруткой:

- `Сводка`
- `Пользователи`
- конкретный тикет в `Жалобах`
- `Аудит лог`

Для `Жалоб` полезно отдельно просить:

- скрин unread badge в левой навигации
- скрин списка тикетов до открытия
- скрин того же списка после открытия тикета

Для `Аудит лога` полезно отдельно просить:

- скрин после фильтра по актёру
- скрин после фильтра по периоду
- скрин после действия, которое обязано было попасть в log

## Как Проверять Premium Flow

Если проверка касается premium, всегда полезно уточнять:

- premium включён или выключен
- тестируется locked-state или unlocked-state
- используется ли debug purchase layer

Debug-механизмы и ограничения production rollout описаны отдельно в [docs/debug-flags.md](/Users/devisjjones/Documents/tinychok/docs/debug-flags.md).

## Ограничения И Безопасность

- не просить присылать в чат секреты, пароли, `.env` или содержимое `htpasswd`
- если нужен результат команды с секретами, просить только безопасный фрагмент или скрин без секретных значений
- при ссылках на `сегодня`, `вчера`, `после полуночи` использовать точные даты, если это влияет на понимание бага
- если проверяется SSL / cert warning, просить:
  - скрин браузерного предупреждения
  - вывод `curl -Iv https://admin.staging.tinychok.ru`
  - без пересылки приватных ключей, `.pem` и содержимого `htpasswd`

## Контекст Staging

- `staging.tinychok.ru` закрыт через basic auth
- backend staging ограничен allowlist-ом телефонов
- при любых ручных проверках staging нужно учитывать оба этих ограничения доступа
