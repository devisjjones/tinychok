# Collaboration Instructions

Короткая памятка по тому, как давать ручные инструкции владельцу проекта в этом репозитории.

## Формат ручных инструкций

- если действие должен выполнять человек, инструкция разбивается на отдельные блоки `Шаг 1`, `Шаг 2`, `Шаг 3`
- в одном шаге лучше давать один логический кусок действий
- после шага нужно явно писать, что ожидается в результате, если это важно для проверки
- если проверка визуальная или зависит от состояния UI, нужно просить скриншот после нужного шага
- если шагов много, имеет смысл просить скриншот после ключевых точек, а не только в самом конце
- если правка касается иконок, аватарок, шрифтов, emoji picker или другой свежей статики, сначала просить жёсткое обновление страницы
- если проверка завязана на server-driven snapshot или lazy history, просить отдельные скрины:
  - сразу после входа в комнату
  - после скролла вверх и догрузки истории

## Ограничения и безопасность

- не просить присылать в чат секреты, пароли, `.env` или содержимое `htpasswd`
- если нужен результат команды с секретами, просить только безопасный фрагмент или скрин без секретных значений
- при ссылках на "сегодня", "вчера", "после полуночи" использовать точные даты, если это влияет на понимание бага или проверки
- не просить присылать `TINYCHOK_CAPTCHA_SECRET_KEY`, analytics tokens или любые внешние ingest credentials

## Как ссылаться на staging-кандидат

- не ссылаться по привычке только на `55304e7`: актуальный уже запушенный candidate сейчас `80346d7`
- если речь именно про уже запушенное состояние ветки, можно говорить `последний запушенный candidate 80346d7`
- если речь про текущую локальную работу, нужно сначала проверить, есть ли новые commits поверх `80346d7`
- если речь про текущий photo / attachment batch до push, нужно явно говорить `локальный HEAD поверх 80346d7`, а не путать его с уже выложенным staging state

## Контекст staging

- `staging.tinychok.ru` закрыт через basic auth
- backend staging ограничен через `TINYCHOK_ALLOWED_TEST_PHONES`
- для любых ручных проверок staging сначала учитывать эти два ограничения доступа
- если просим проверить cumulative staging-кандидат, полезно явно писать, что проверяется весь накопившийся stack, а не один локальный UI-фикс
- если проверяем треды, полезно просить отдельные скрины:
  - списка в разделе `Треды`
  - самого thread room
  - badge на кнопке `Треды` после нового ответа
- если проверяем delete-баги на staging, нужно просить сценарий именно с повторным входом:
  - удалить сообщение
  - выйти из комнаты
  - зайти в комнату снова
  - при необходимости сделать hard reload
  - только после этого делать вывод, что delete-path реально починен
- если проверяем photo / attachment batch, нужно просить отдельные скрины:
  - compose preview до отправки
  - сообщение после отправки в ленте
  - fullscreen viewer после tap по фото
  - locked-state `Отправить без сжатия` у non-premium
